## 修正后的理解

### 1. Search-R1 和普通 RAG 的最大区别

原始回答“能主动搜索信息”是对的，但还需要补上关键细节：

- 普通 RAG 的检索通常由系统固定触发，例如先检索一次，再把文档塞给模型。
- Search-R1 的检索由模型输出动作触发，模型自己决定是否生成 `<search> query </search>`。
- 这个搜索动作会进入 RL rollout，最终由 reward 反馈影响模型策略。

一句话版本：

> Search-R1 不是固定流程 RAG，而是让模型通过强化学习学会何时搜索、搜什么、何时停止搜索并回答。

### 2. 三个标签的角色

`<search>` 是模型发出的工具调用动作。

- 模型如果缺少外部知识，就生成 `<search> 查询词 </search>`。
- 在 `infer.py` 中，`get_query()` 会从模型输出里解析这个标签。

`<information>` 是检索服务返回给模型的观察结果。

- 它不是模型自己凭空生成的答案。
- 它来自 `/retrieve` 检索服务返回的文档。
- 代码会把检索结果包进 `<information> ... </information>`，再拼回 prompt，让模型继续推理。

`<answer>` 是模型给出的最终答案动作。

- 模型认为不需要继续搜索时，就输出 `<answer> 最终答案 </answer>`。
- 后续 reward 会根据这个答案和标准答案计算得分。

### 3. 为什么更适合大模型求职项目

原始回答“符合 JD”方向正确，但面试时要讲得更具体：

- Agent 能力：模型通过 `<search>` 主动调用工具。
- RAG 能力：项目包含 BM25、Dense、在线搜索等检索方案。
- RL 能力：项目用 PPO/GRPO 训练搜索和回答策略。
- 工程能力：项目涉及 vLLM、veRL、FastAPI 检索服务、数据处理、训练配置。
- 评估能力：后续可以扩展 trajectory logger、failure analysis 和消融实验。

更完整的一句话：

> 这个项目比普通 RAG demo 更适合求职，是因为它同时覆盖 Agentic RAG、tool calling、RL rollout、reward 设计、检索服务和训练工程。

## 今日源码定位

- `infer.py` 中的 `curr_search_template` 定义了如何把检索结果包进 `<information>`。
- `infer.py` 中的 `get_query()` 负责从模型输出中解析 `<search>`。
- `infer.py` 中的 `search()` 负责请求本地 `/retrieve` 服务。
- `infer.py` 中的主循环会把检索结果拼回 prompt，让模型继续生成。

## infer.py 推理闭环

### 1. 输入问题和协议

`infer.py` 先指定一个问题，然后在 prompt 中规定模型必须使用四类标签：

- `<think>`：先思考。
- `<search>`：缺少知识时发起搜索。
- `<information>`：接收检索系统返回的信息。
- `<answer>`：输出最终答案。

关键理解：这些标签不是装饰，而是 Search-R1 的工具调用协议。

### 2. 停止条件

`StopOnSequence` 的作用是：模型一旦生成 `</search>`，本轮生成就暂停。

原因是代码需要立刻解析 `<search> query </search>` 中的 query，然后调用检索服务。如果不暂停，模型可能继续往下编造 `<information>`，这会破坏工具调用闭环。

补充理解：

- “防止无限输出”只是次要原因。
- 更核心的原因是：模型生成 `</search>` 表示它已经发出了一个工具调用动作，此时程序必须暂停模型生成，把控制权交给 Python 代码。
- Python 代码解析 query，调用 `/retrieve`，拿到真实检索结果，再把结果作为 `<information>` 拼回 prompt。
- 如果不暂停，模型可能自己继续生成 `<information>`，那就不是外部检索结果，而是模型幻觉。
- `StopOnSequence.__init__()` 只是在准备停止规则：把 `</search>` 这些字符串转成 token id。
- 真正判断是否暂停发生在 `StopOnSequence.__call__()`：每次生成新 token 后，Transformers 会调用它检查当前输出尾部是否匹配 `</search>`。
- 真正把规则交给生成器的是 `model.generate(..., stopping_criteria=stopping_criteria)`。

一句话版本：

> `</search>` 是工具调用的断点，模型到这里必须停下来等外部工具返回结果。

更精确的一句话：

> `__init__()` 只是登记停止词；`__call__()` 才是判断是否命中停止词；`model.generate()` 负责在生成过程中反复调用这个判断函数。

### 3. 搜索调用

`get_query()` 从模型输出中提取最后一个 `<search>...</search>`。

`search()` 把 query 包成如下请求：

```python
payload = {
    "queries": [query],
    "topk": 3,
    "return_scores": True
}
```

然后请求本地检索服务：

```python
requests.post("http://127.0.0.1:8000/retrieve", json=payload)
```

关键理解：LLM 本身不直接查资料，它只输出工具调用意图；真正查资料的是 `/retrieve` 服务。

### 4. 把检索结果拼回 prompt

检索结果会被格式化成：

```text
<information>
Doc 1(...)
Doc 2(...)
Doc 3(...)
</information>
```

然后追加回 prompt，模型在下一轮生成时就能看到这些外部信息。

### 5. 什么时候停止

如果模型生成的是 `<answer>...</answer>` 或者输出结束符，代码就打印结果并退出循环。

如果模型生成的是 `<search>...</search>`，代码就继续搜索并进入下一轮。

## 今日一句话总结

`infer.py` 展示的是 Search-R1 的最小推理闭环：模型先思考，缺知识就输出 `<search>`，代码调用 `/retrieve`，再把结果作为 `<information>` 喂回模型，直到模型输出 `<answer>`。

## 教学方式调整：自顶向下

后续学习按这个顺序推进：

1. 先问“这个文件在系统里解决什么问题”。
2. 再画“输入、状态、动作、外部工具、输出”的数据流。
3. 然后找关键抽象，例如 prompt 协议、停止条件、动作解析、检索工具。
4. 最后才进入具体函数和行级代码。

`infer.py` 的顶层角色：

- 它不是训练脚本。
- 它不是检索服务。
- 它是一个最小推理演示脚本，用来展示训练后的 Search-R1 模型如何进行多轮搜索和回答。

`infer.py` 的顶层数据流：

```text
question
-> prompt
-> model.generate()
-> <search> query </search>
-> Python 解析 query
-> /retrieve 返回文档
-> <information> 文档 </information>
-> prompt 追加新信息
-> model.generate()
-> <answer> 最终答案 </answer>
```

关键理解：

> `infer.py` 的核心不是“生成文本”，而是“让模型生成动作，让 Python 执行动作，再把外部观察结果交还给模型”。
